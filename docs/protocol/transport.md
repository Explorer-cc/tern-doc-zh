# 传输

TSP 通过 APC 字符串在窗格的 pty 上带内传输。这种方式可通过 ssh 工作，与程序写入的所有其他字节保持顺序，并允许 Tern 的会话守护进程保留并重放界面，而无需第二个通道。

## 帧格式

```text
ESC _ tsp ; <verb> [; <key>=<value>]* ; <body> ESC \
```

- `verb` 是一个字母（见下文），区分大小写。
- `verb` 后的片段只有在符合 `key=value` 格式（key 为 `[A-Za-z0-9_-]+`，value 为可打印 ASCII 字符但不含 `;`，且不含空格），并且后面还有一个 `;` 时，才是参数。第一个不符合该格式的片段会开始正文，因此含有 `;` 或 `=` 的 JSON 正文仍保持完整；没有参数的消息就是 `tsp;<verb>;<body>`。
- `body` 是 UTF-8 JSON，或在 `b` 消息中为 base64。JSON 会转义每个控制字符，因此正文不会包含 ESC 或 BEL；Tern 将字符串中的 8 位 `0x9C` 视为负载而非终止符，因此原始 UTF-8 是安全的。无效 JSON 正文会产生 `error` 事件：`{"ev":"error","msg":"malformed f body: …"}`。
- 每条消息都以 7 位 ST `ESC \` 结尾。与 kitty 一样，Tern 的解析器也会在 BEL 处结束任何字符串，但 TSP 只定义 ST：绝不要发送以 BEL 结尾的 TSP。
- 两个方向都会忽略未知 verb 和未知 JSON 字段（未知 verb 不会产生 `error`）。新增字段永远是可选的；不兼容的更改会提升协议版本（见[握手](handshake.md)）。

Tern 读取的参数：

| 参数 | 适用范围 | 含义 |
| --- | --- | --- |
| `c`, `m` | 任意 verb | [分块](#分块) |
| `mime` | `b` | blob 的 MIME 类型（[Blob](#blob)） |
| `key`, `buf`, `seeded` | `o` | 为 Tern 会话守护进程重放的快照保留，且仅在此处读取：程序发送的 `o` 中这些参数会被忽略。 |

| 动词 | 方向 | 含义 |
| --- | --- | --- |
| `q` | 程序 → 终端 | 查询：`hello`、blob 是否存在（[握手](handshake.md)） |
| `o` | 程序 → 终端 | 打开一个界面（[界面](surfaces.md)） |
| `f` | 程序 → 终端 | 一帧：文档操作的原子批次（[文档和帧](documents.md)） |
| `b` | 程序 → 终端 | 一个 blob（见下文） |
| `t` | 程序 → 终端 | 已废弃；忽略（[样式表和图标](theme.md)） |
| `s` | 程序 → 终端 | 一个样式表（[样式表和图标](theme.md#样式表)） |
| `x` | 程序 → 终端 | 关闭一个界面（[界面](surfaces.md)） |
| `r` | 终端 → 程序 | 对 `q` 的回复 |
| `e` | 终端 → 程序 | 一个事件（[输入和事件](input.md)） |

终端 → 程序的消息经由 pty 的*输入*端传输，类似 DA 或 OSC 11 的回复；每条消息都是一个不带参数的 `ESC _ tsp;<verb>;<json> ESC \` 字符串：Tern 不会对它们分块。读取输入时，应使用能够接收任意长度完整 APC 字符串的转义序列缓冲区（携带表单值的事件可能很长），并在按键处理之前将 `ESC _ tsp;` 字符串路由到你的 TSP 代码。绝不要回显或打印它们。

下面是一帧示例：它追加流式 Markdown 并将卡片标记为完成：

```text
ESC _ tsp;f;{"sf":"s1","s":812,"ops":[["text","a41","append"," and then the parser"],["set","t9",{"tone":"success","status":"done"}]]} ESC \
```

## 分块

正文超过协商得到的 `apc` 限制（65 536 字节，除非 hello 回复另有说明）时，应拆分为多条具有相同 verb 的消息；每条消息都带有 `c=<chunk-id>`（由你选择的令牌），除最后一块外，每块还带有 `m=1`。Tern 会在解析前逐字节拼接正文，因此拆分点可以落在 UTF-8 字符中间，但不能使下一块正文以类似参数的片段开头（见下文）。拼接后的消息保留第一块的其他参数（例如 blob 的 `mime`）；后续块的参数会被忽略：

```text
ESC _ tsp;f;c=k7;m=1;{"sf":"s1","s":9,"ops":[["text","log","append","…first 65 000 bytes… ESC \
ESC _ tsp;f;c=k7;…the rest…"]]} ESC \
```

Tern 一次只拼接一个序列，因此同一消息的分块必须连续发送。当任何 TSP 消息（没有 `c`、另一个 `c` 或另一个 verb）不是该序列的下一块时，序列会被丢弃并产生 `error` 事件：`{"ev":"error","msg":"chunked f message c=k7 dropped: interrupted"}`。如果 1 秒内没有收到下一块（`timed out`），或拼接后的正文超过限制，也会丢弃序列：帧为 400 000 000 字节，其他消息为 24 MiB（`over 25165824 bytes`）。因大小而丢弃的序列，其余部分会被跳过，直到最后一块。RIS 会静默丢弃序列。中断序列的消息仍会单独处理。

不要为了适应限制而拆分一帧：该限制远高于窗格的保留预算，超过预算的文档会被裁剪（[保留](operations.md#保留)），因此恢复长记录的帧应整体发送。

每块都会像任意消息一样解析参数，因此块正文自身不得以类似参数的片段开头：以 `x=1;y…` 开头的 JSON 块会静默地把 `x=1` 当作参数丢弃。若拆分点会造成这种前缀，就应移动拆分点：紧挨 `;` 之前，或任何非 `A`–`Z`、`a`–`z`、`0`–`9`、`_`、`-` 字节之前拆分，总是安全的。Base64 不含 `;`，因此 blob 分块是安全的。Tern 自己的分块器（其会话守护进程重放的快照）也遵循相同规则。

Tern 的解析器会放弃超过 262 144 字节的 APC 字符串（计入 `ESC _` 之后的所有内容，包括参数），且不会产生 `error`；该字符串的其余部分随后会作为文本显示在屏幕上。Tern 接受不超过该大小的单条字符串，但每块应控制在 `apc` 限制以内。

## Blob

`b` 发送二进制数据，供 `image` 节点显示为图像，发送一次即可：

```text
ESC _ tsp;b;mime=image/png;<base64> ESC \
```

- 正文是标准 base64（`+/`、`=` 填充，不带换行）。Tern 遇到错误的 base64 会产生 `error` 事件。
- blob 的 id 是其解码字节的 SHA-256 小写十六进制值（64 位数字）。不会发送该值：Tern 会对收到的数据进行哈希；你也要自行对字节进行哈希，以便在 `image` 节点或 `blobs` 查询中命名该 blob。Tern 会忽略 `id` 参数。
- `mime` 是可选的。
- 解码后的 blob 最多为 16 MiB，且像任意消息一样分块（首块带 `mime`）。
- Blob 以内容寻址，在窗格的各个界面之间共享，并由 Tern 保存在磁盘上，因此恢复的屏幕会显示图像而无需重新发送；如果某个窗格从未收到过此 blob，命名该 blob 的 `image` 节点也会在另一个窗格发送过它时，从磁盘副本中绘制图像。通过 `blobs` 查询询问还需要发送哪些内容（[握手](handshake.md#其他查询)）。

### 通过 Tern 的 blob 缓存

在保存 Tern blob 缓存的机器上运行的程序，可通过 `TERN_BLOB_DIR` 找到缓存目录：Tern 会为它启动的每个窗格设置此变量，而 ssh 不会传递该变量。无需通过 pty 发送 blob 字节，改为：

1. 将字节写入 `$TERN_BLOB_DIR/<id>`，其中 id 是 blob 的 SHA-256 小写十六进制值：先在该目录写入 `<id>.tmp<pid>`，然后重命名，这样 Tern 就不会读取到不完整的文件。如果 `<id>` 已存在，则跳过此步骤。
2. 针对该 id 发出 `blobs` 查询。Tern 会读取文件，检查其字节哈希是否与文件名一致，并在 `have` 中列出该 id；它会根据字节判断图像类型。
3. 按照通常方式，用 `b` 发送 `have` 中缺失的每个 id。

你可以在回复到达之前发送显示该图像的帧。

## Windows

在 Windows 上，pty 是 ConPTY，其 host（`OpenConsole.exe` 或 conhost）在两个方向上都位于 Tern 与程序之间。

**终端 → 程序。** ConPTY 的输入解析器会丢弃 APC 字符串，因此 `ESC _ tsp;…` 输入永远不会到达程序。它会原样传递 OSC 字符串，所以 Tern 会将终端 → 程序消息写入 ConPTY，格式如下：

```text
ESC ] 877 ; tsp ; <verb> [; <key>=<value>]* ; <body> ESC \
```

正文逐字节保持相同，但 U+0080–U+009F 除外：解析器会处理字符串中的 C1 控制字符，而 U+009C 会终止字符串，因此这些码点（只会出现在 JSON 字符串内部）会以 JSON 转义 `\u0080`…`\u009f` 传输。应同时接受这两种帧格式，以及以 BEL 结束的 OSC 877，并将它们一视同仁。OSC 877 只会用于终端 → 程序方向；macOS 和 Linux 上的终端仍使用 APC。

**程序 → 终端。** 消息仍使用 APC。Windows 自带的 conhost 会重新渲染程序输出并丢弃 APC，因此 TSP 需要使用 Tern 随附的 ConPTY（`conpty.dll` 和 `OpenConsole.exe`，安装在 `tern.exe` 旁边）。该 host 会原样将程序输出写入终端，并将 DA1 等查询交给终端处理，因此 hello 及其 DA1 哨兵会按顺序到达 Tern，并按顺序得到答复。
