# 生命周期与重新加载

运行插件的进程启动时，插件随之加载；每当插件文件夹发生变化或有人请求时，插件都会整体重新加载。重新加载会替换该上下文中的每个 VM；运行中的块会通过已保存状态延续，运行中的 Lens 捕获则会在原工作线程上完成。本页介绍事件发生的顺序、重新加载的触发条件，以及重新加载或守护进程重启后哪些内容会保留。

## 加载

两端加载时都先扫描插件文件夹（[包与清单](packages.md#目录)）：将包按 id 排序，单独记录扫描问题，并将设置中已关闭的插件标记为 Disabled。

**Host 端**在会话守护进程启动时加载，早于其恢复已保存的窗格，因此恢复的块能找到对应的块类型。没有守护进程、由窗口运行其窗格时，则在窗口创建第一个窗格时加载。每个获准且包含 `host` 入口的包都会获得一个工作线程，该线程创建 VM 并在 2 s 的 Host 端时间预算内运行入口；所有工作线程会同时启动，Host 端会等待每个工作线程报告。若插件入口抛出异常，或未定义已声明的块或 Lens，该插件会标记为 Failed；其他插件照常加载。

**Window 端**在窗口创建时加载，顺序位于 Tern 自身的样式表之后、首次应用按键映射之前。在窗口的 UI 线程上，按 id 顺序为每个获准的包安装其 manifest 样式，然后在 50 ms 的 Window 端时间预算内运行其 `window` 入口。入口失败时会显示提示消息“Plugin *name* failed to load”，其中包含错误的第一行，并在该窗口中将插件标记为 Failed。所有入口运行完毕后，窗口会读取它们注册的内容：命令面板条目、按键映射的插件层、chrome 格式化器和 `tern.css` 样式表。

**`window_start`** 在每个窗口中针对每个插件运行一次，且在窗口会话稳定下来（已恢复或刚启动）之后运行，因此工作区脚本在添加标签页时能看到会话中已有的标签页。参见[布局与工作区](../guides/layout.md)。

凡是插件需要轮流处理的场景（覆盖项、路由、chrome 格式化器、`spawn` 过滤器、Lens 声明），顺序均为插件 id 顺序。

## 目录与状态

每一端都会为每个插件单独维护状态：

| 来源 | 报告的状态 |
| --- | --- |
| Host 目录 | 对 host 入口报告 Ready、Disabled 或 Failed。只要设置允许，没有 host 入口的插件在此处就是 Ready。 |
| Window | 对该窗口中的 window 入口报告 Ready、Disabled 或 Failed。 |

Host 的目录是它发送给窗口的内容（参见[架构](architecture.md#目录)），也是 `tern plugin list` 打印的内容：运行中守护进程的目录；若没有守护进程，则读取文件夹但不运行任何插件（每个获准的包均为 Ready）。因此，失败的 window 入口不会在 `tern plugin list` 中显示为 Failed。

“偏好设置 › 插件”会针对每个本地插件显示 host 和 window 状态中较差的一项，并以只读方式按主机名称列出已连接远程主机的插件。

每当 Host 端的目录发生变化（窗口连接时，以及目录变化后的重新加载完成时），且其中存在问题或 Failed 插件，窗口就会显示一条提示消息：“1 plugin has problems”或“*N* plugins have problems”，并在下方显示第一条错误。

## 监视

插件文件夹以及其中每个位于文件夹外部的包目录（`.path` 链接和符号链接的目标）都会受到监视：

| 平台 | 机制 |
| --- | --- |
| macOS | FSEvents，递归监视 |
| Linux | inotify，每个目录一个监视项（包目录最多深入 8 层） |
| Windows | `ReadDirectoryChangesW`，递归监视 |
| iOS，以及监视不可用的环境 | 每 2 s 对目录树指纹进行一次轮询（路径、大小、修改时间；8 层、10,000 个条目） |

监视不可用时（例如网络卷，或 Linux 的 inotify 监视项耗尽），会退回轮询。更改会按 300 ms 的时间窗口合并处理。任何更改都会重新加载监视上下文中的所有插件，而不只是发生变化的包。

守护进程和每个窗口各自独立监视：守护进程重新加载 Host 端，窗口重新加载 Window 端。

## 重新加载

| 触发条件 | Host 端 | Window 端 |
| --- | --- | --- |
| 受监视文件夹发生变化 | 守护进程（或没有守护进程时运行窗格的窗口）重新加载；若目录有变化，守护进程会将其发送给每个窗口 | 机器上的每个窗口根据各自的监视结果重新加载 |
| `tern plugin reload` | 守护进程重新加载并返回其目录，同时也会将目录发送给每个窗口 | 收到其守护进程发送的目录后，这台机器上的窗口会重新加载 |
| `tern plugin reload ID` | 与 `tern plugin reload` 相同，但仅针对插件 `ID`；其他插件继续运行 | 这台机器上的窗口仅重新加载插件 `ID` |
| `tern plugin install`、`remove`、`link`、`unlink` | 更改完成后，行为与 `tern plugin reload` 相同 | 与 `tern plugin reload` 相同 |
| 命令面板：Reload plugins | 窗口连接的每个主机（包括远程主机）都会重新加载；没有守护进程的窗口会重新加载自身运行时 | 此窗口重新加载 |
| 偏好设置 › 插件：开关、Reload、Install… | 与命令面板命令相同 | 此窗口重新加载 |

`tern plugin reload` 需要运行中的守护进程（否则会提示 `no daemon running`）。修改类动词无需守护进程也能运行，并会打印 `no daemon running; changes apply at next start`。参见[命令行](../reference/cli.md)。

一次编辑通常会让窗口重新加载两次：一次来自窗口自己的监视，另一次来自守护进程发送的新目录。如果某次窗口重新加载的加载失败与上次完全相同，就不会再次为这些失败显示提示消息；目录的提示消息也只会在目录变化时显示，因此插件发生故障时每次更改只会报告一次，而不是每次重新加载都报告。

如果在窗口处理器运行期间请求重新加载（例如由定时器触发，或由编辑插件文件夹的命令触发），则会在该处理器返回后执行。

## 重新加载后保留的内容

**Host 端。**旧工作线程会退役，并根据当前文件夹和设置启动新的工作线程。

| 内容 | Host 端重新加载后 |
| --- | --- |
| 运行中的块 | 移至新工作线程并重新启动：`init(cx, args, saved)` 会使用其上次 `save` 返回的状态运行（对于类型没有 `save` 的块，状态为 `nil`）。窗格保持不变；其视图会重建。 |
| 类型已不存在的块 | 插件已移除、禁用或失败，或块已从 manifest 中移除：该块会以 `no block type KIND on this host` 结束，退出状态为 1。 |
| 运行中的 Lens 捕获 | 在旧代码下于旧工作线程上完成；最后一个捕获完成后旧工作线程退出。新命令会发送到新工作线程。 |
| 已完成的 Lens 捕获 | 其 Lua 状态随旧 VM 一同消失；此类块的下一次事件会在新工作线程上重建状态（见下文[重新水合](#lens-重新水合)）。 |
| 钩子、`spawn` 过滤器、定时器、待处理的进程和 fetch 回调 | 随旧 VM 结束；新入口会注册自己的内容。 |
| 因超出时间预算而暂停的钩子 | 立即再次运行：VM 已是新的。 |
| `tern.kv`、数据文件夹中的文件 | 保持不变。 |

**Window 端。**窗口会丢弃每个插件 VM 并重新构建。

| 内容 | Window 端重新加载后 |
| --- | --- |
| Lua 状态、注册内容 | 消失；入口会重新运行并重新注册。 |
| 插件样式表 | 移除并重新安装 `plugin:local:*` 样式表。 |
| 按键映射、命令面板行、格式化器 | 根据新的注册内容重建。 |
| `window_start` | 仅针对尚未在此窗口运行过该函数的插件运行：新添加或新启用的插件会运行；已运行过的插件不会运行。 |
| 因超出时间预算而暂停的钩子 | 立即再次运行。 |

Window 端跨重新加载所需的内容应放在 `tern.kv` 或文件中；块所需的内容应放在其 `save` 结果中。

## 守护进程重启与升级

**重启。**守护进程启动时若发现已停止的守护进程（退出、崩溃或机器重启）留下的状态文件，就会先加载插件，再恢复已保存的窗格。Shell 会作为登录 shell 恢复；若某个 shell 正在运行 agent CLI（`claude`、`codex`、`omp`、…）、终端编辑器、监视器或分页器，它会在首次提示符处再次运行该命令行；报告过自身 id 的 agent 会话则会恢复。其他内容（构建、服务器、脚本）不会再次运行。插件块会以相同的块类型恢复，并从其 `save` 上次返回的状态启动；恢复时尺寸保持不变，屏幕为空白。该块视图之外的内容都不会保留，而且块绝不会作为 shell 恢复。若 host 上没有 Ready 插件再定义该块类型，则不会恢复窗格（守护进程会记录 `cannot restore plugin block`）。如果窗格恢复时发生内部错误（panic），也会以相同方式将其排除，其他窗格仍会恢复；若窗口无法从已保存的布局恢复某个块，就会将它从分屏中排除，并在通知中指出它。

**原地升级（Unix）。**升级会将守护进程移交给新构建版本，而不终止任何程序：shell 会保留其伪终端、屏幕和回滚区。插件块没有伪终端：移交前插件会停止，并保留其最后保存的状态；新守护进程会像恢复一样，从该状态重新启动每个块。工作线程上的 Lens 状态不会保留。

编写 `save`，确保其结果足以重建块。参见[块](../guides/blocks.md)。

## Lens 重新水合

Lens 状态只存在于工作线程的 VM 中，每个插件最多保留最近 256 次捕获。Lens 块的生命周期更长：重新加载、守护进程重启或升级之后，或捕获被逐出后，块仍会保留其命令行、工作目录、原始输出、宽度和退出状态。

此类块发送事件时（点击带有 action 的节点、进行选择或切换），Host 端会将该记录连同事件一起传给工作线程。工作线程会再次根据插件的 `match` glob 判断是否认领该命令；如果仍然匹配，就运行 `open`，然后对按块宽度重放的已保存输出逐行运行 `line`，若命令已结束则运行 `finish`，接着运行事件处理器，并发送新视图。如果 glob 不再匹配该命令，则不会运行任何内容。

重新水合会重新运行处理器，包括其中的任何副作用（提示消息、进程、文件写入）。请确保 `open`、`line` 和 `finish` 不包含只应发生一次的副作用。参见[命令 Lens](../guides/lenses.md)。
